## 1. P1 — Camera decoding can preempt student selection

**Where:** `artifacts/web/src/features/scanner/ScannerPage.tsx:74-85,276-279,298-304`.

**Why:** The typed partial-ID path sets `choices` and returns before setting
`busy.current`. Camera pause considers only `answer` and `checking`, not
`choices`. A camera detection during selection therefore enters `scan` with
`source === "camera"`, clears the choices, and checks in a different student
without the operator completing the pending selection.

**Reproduction:** With a working camera, type an ambiguous partial ID, leave
the pick list open, then present another student's QR. The camera path remains
enabled and replaces the pending choice with its scan.

**Evidence:** Source-confirmed. The running browser rendered the pick list,
but had no camera, so live QR preemption was not exercised.

**Suggested fix:** Pause camera processing while choices exist and guard the
decode handler against a pending choice. Resume only after explicit selection
or cancellation. Add a test that invokes a decode while candidates are shown
and asserts no scan request is submitted.

## 2. P2 — A pending student choice loses its event context

**Where:** `artifacts/web/src/features/scanner/ScannerPage.tsx:57-60,89-93,233-246,298-304`.

**Why:** Choices store candidates and total, but not the originating event.
Changing the event selector leaves the same choices visible. A roster refresh
that closes the selected event can also automatically select another open
event. Picking a student then uses the current event, not the event for which
the operator originally entered the partial ID. This can silently record
attendance for the wrong event.

**Reproduction:** With two open synthetic events, open an ambiguous-ID choice
for event A, switch to event B, then choose a student. The callback submits
event B. The automatic fallback after A closes has the same interaction.

**Evidence:** Source-confirmed; event-switch-during-choice was not separately
exercised in the browser pass.

**Suggested fix:** Bind choices to their originating event and dismiss or
explicitly reconfirm them whenever that event changes or becomes unavailable.
Include manual selection, automatic fallback, and all-events-closed tests.

## 3. P2 — Report check-in hides the offline/pending state

**Where:** `artifacts/web/src/features/report/ReportPage.tsx:65-71,237-242,277`;
`artifacts/web/src/offline/submit.ts:96-103`.

**Why:** The report passes the offline flag to `describeResult`, but keeps only
`title` and discards its offline explanation. An offline prediction is shown
as an ordinary "Checked in" notice, and the pending overlay makes the row
look confirmed. The report has no sync-status or reconciliation-issues
display. Staff cannot distinguish a saved-on-device prediction from attendance
confirmed by the server, or readily see a later rejection without leaving
the report.

**Reproduction:** Cache a synthetic roster, make scan submission unavailable,
then click a report Check in button. `submitScan` returns `kind: "offline"`,
but the report formats the same success title used for an online answer.

**Evidence:** Source-confirmed. The browser verified the scanner's explicit
offline message; the report offline path was not separately exercised.

**Suggested fix:** Include the offline explanation in the report feedback and
show persistent pending/sync/error status, including reconciliation issues.
Test queued success and subsequent server rejection on the report itself.

## 4. P2 — A late roster fetch can revert a successful event toggle visually

**Where:** `artifacts/web/src/features/events/EventsPage.tsx:29-39`;
`artifacts/web/src/offline/hooks.ts:23-30`.

**Why:** PATCH success replaces the event in the query cache without cancelling
an outstanding roster read. A read containing the old state can finish
afterward and overwrite the successful update. The switch and scanner event
availability then show the old state until another refresh. An operator
retrying the apparently failed change may send another unintended update.

**Reproduction:** Hold a roster fetch returning a closed synthetic event,
finish a successful PATCH opening it, then release the old fetch.

**Evidence:** Reproduced using the installed TanStack QueryClient and a deferred
synthetic query: the cache was open after the toggle update, then closed after
the older read resolved. The browser separately verified a normal successful
mocked toggle.

**Suggested fix:** Protect the event cache update with query cancellation and
appropriate revalidation. The registration update path already addresses this
race in `artifacts/web/src/offline/roster.ts:18-28`. Add a delayed-read test for
event toggles.

## 5. P2 / product clarification — Closed events still offer ordinary Check in

**Where:** `artifacts/web/src/features/report/ReportPage.tsx:165-168,249-262,52-61`.

**Why:** The report offers every event, does not label its open/closed state,
and displays Check in for active unchecked attendees regardless of closure.
The scan rules also accept these new submissions. Closing an event removes it
from the scanner, but an admin can still initiate new check-ins through the
report with no indication that this differs from normal event operation.

**Evidence:** Browser-confirmed using a synthetic closed event: its unchecked
attendees still had enabled Check in controls. The permissive server scan
contract predates this UI; this is not a newly introduced backend bypass.

**Suggested fix:** Decide whether report check-in is an intentional override.
If not, disable fresh report check-ins when the selected event is closed. If
it is, label closure and make override behavior explicit. Preserve acceptance
of already-queued offline scans: rejecting all submissions for closed events
would break that existing replay contract.

## 6. P3 — Every event-update failure is presented as a connection problem

**Where:** `artifacts/web/src/features/events/EventsPage.tsx:40-42`.

**Why:** The catch-all always shows the connection-required message, including
permission denial, a deleted event, or a server error while connected. It
directs the operator to check networking instead of explaining the actual
problem.

**Evidence:** Browser-confirmed with a mocked HTTP 403 and an aborted PATCH:
both produced the same connection-required notice. Event state correctly
remained unchanged.

**Suggested fix:** Distinguish connectivity failures from authorization,
not-found, and server failures. Reuse the app's error helpers and provide a
retry or reauthentication action where appropriate.
